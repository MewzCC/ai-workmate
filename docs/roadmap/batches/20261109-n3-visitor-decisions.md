# N3 访客受控审批与驳回

基线 `26e94bea`，实施依据为[业务缺口计划](../20261109-missing-business-capabilities.md)的 N3 / G03。

## 实施边界

- 新增两个固定 L2 原子工具，默认关闭，复用领域审批事务；不增加任意页面点击、远程地址、递归工具或批量审批。
- 输入是审批任务编号、任务版本、审批意见；驳回理由必填。预约编号和预约版本单独投影，不可冒充审批任务坐标。
- 查询仅向具备实时审批资格的当前处理人投影任务编号与版本；领域重新校验租户、任务、预约、实例、申请人、状态和版本。
- 访客与后续用印共用稳定决策参数与回执结构；领域入口和具体权限保持独立。
- 审批成功只表示允许后续到访，不自动签到、到访、离场。

## 检查发现与裁定

现有访客决策使用独立事务的业务审计，且未核对任务实例与预约实例的完整关联。本批将审批审计和通知收敛到同一业务事务，并增加资源绑定校验；这些是安全开放 Agent 决策的必要前提，不扩大普通员工权限。旧人工入口继续复用同一领域方法。

回执导航检查发现访客页此前缺少按编号读取详情的路由实现。本批增加固定 `/oa/visitor-booking?id=<预约编号>` 与认证详情弹窗，不把审批任务编号当作预约编号。封装的 `useBusinessRecordDetail` 只接收固定页面及代码提供的认证加载函数，按身份 / 权限 scope 拒绝迟到响应；N4 可复用该读详情机制。

## 合约与迁移

- `visitor.approve` / `visitor.reject` 输入 `taskId`、任务 `version`、`comment`，驳回理由必填；独立工具权限分别为 `agent:tool:visitor.approve` / `agent:tool:visitor.reject`，领域权限为 `approval:act`。
- 共用 `WorkflowDecisionToolModels` 的回执含 `resourceId`、固定 `resourceType=VISITOR_BOOKING`、`resourceStatus`、`resourceVersion`、`taskId`、任务 `status` / `version` 和 `action`。不会将整条访客实体、电话、车牌或内部身份返回模型。
- 领域审批锁定预约记录，核对任务和实例的租户、类型、业务编号、申请人、处理人、状态与版本；同一预约的并发通过 / 驳回只有一方能提交。
- 新增 `V202611091100` 注册默认关闭的两个 L2 工具，并仅升级已知旧 Schema 的 `visitor.query` 契约；不改历史迁移、不改启用开关。未知租户自定义 Schema 保持原状并继续由 Registry 失败关闭。
- 查询的新任务坐标为可选受控字段，只有 `canDecide=true` 的当前受理人获得；旧冻结查询任务不重写快照，升级后需重新规划。
- 已成功的旧查询历史仍可读取；历史结果缺少两个任务坐标时，只显示历史预约信息与“重新查询当前待办”的提示，不补造任务编号或版本。部分坐标损坏仍失败关闭。
- 人工审批和 Agent 审批共用业务事务；业务审计和站内通知均采用 REQUIRED 传播，通知失败时成功审计也回滚。

## 发布与回滚

代码登记增至 155 个工具（50 读、105 写），本批两个写工具保持默认关闭；运行启用仍须独立人工发布门。部署顺序为迁移、匹配版本应用、合同验证，再按发布门开启能力，不修改已持久化的计划。
