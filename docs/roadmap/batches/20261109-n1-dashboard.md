# N1 驾驶舱通用审批入口

基线 `3eb21930`，实施依据为[业务缺口计划](../20261109-missing-business-capabilities.md)的 N1 / G01。此批不新增工具或修改运行写开关。

## 改动与约束

- 待办数量、逾期数量、八项摘要窗口和人工 CSV 导出复用 `UnifiedTodoMapper` 的有效资源关系。任务、实例、业务类型、租户、申请人必须匹配，当前支持请假与通用审批。
- 通用任务标题从对应实例的冻结快照读取，不使用后来编辑的申请标题；快照缺失时只返回安全编号，新增 `detailAvailable=false`，禁止误入同号请假详情。
- 公共固定导航函数按业务类型分派；人工处理 / 查看、页面 `ui.openDetail` 共用这一入口，非法编号、未知类型与缺失详情均拒绝。页面操作仍检查当前待办权限与入口权限。
- 摘要明确最多八项并提供完整待办入口；指标不是摘要数组的长度。导出保留原权限、日期边界、1000 行上限、公式注入处理及审计。
- Agent 的驾驶舱聚合 Port 不返回业务记录，因此 HTTP 摘要新增字段不扩大工具输出或更改冻结 Schema。

## 计划裁定

1. N1 使用统一待办当前已支持的请假 / 通用审批集合；访客、用印在 N5 同步扩展统一投影，不能只扩大数量而缺少摘要和正确详情路径。代价是 N5 交付前它们继续在专属页面办理，界面和文档不宣称已统一。
2. 驾驶舱当前 AI 预审提示及页面能力不能安全区分通用任务。N1 对通用任务的预审明确禁用并提供双语原因，人工详情正常开放；N2 接线时补齐现有通用详情只读工具的页面能力与提示，不把通用编号交给请假工具。任何启用仍受实时权限和 Tool Gateway 约束。
3. 继续在用户指定的 `feature/zcc` 工作区串行提交；当前没有其他用户改动，不新增并行业务工作区。
