# N7 通用审批顺序加签

基线 `972ab51a`，对应[业务缺口计划](../20261109-missing-business-capabilities.md) N7。

## 运行时模型与裁定

- 保留原提交快照、冻结节点及规则，不修改 `approval_execution.plan_json`。复用 `workflow_task.parent_task_id`、`add_sign_mode` 与工作流日志显式记录运行时干预，不增加可执行 JSON、脚本或任意流程解释器。
- 原节点为根任务，加签任务为其一层子任务，保留冻结节点索引。前加签使根任务 WAITING，子任务 PENDING；子任务通过后恢复根任务。后加签在根任务通过后按创建顺序逐个激活；最后一个子任务通过后才前进到下一冻结节点。
- 一次仅允许一个有效 PENDING 任务。审批、加签、转交、抄送与撤回共用申请聚合锁，并在锁内重新读取任务和比较版本。WAITING 不能通过直接请求提前办理。
- 允许根任务在恢复后继续添加不同人员的前加签，以及多个不同人员的后加签。子任务不递归加签；每个根节点最多 20 个加签任务，整个有界执行最多 420 条任务、14000 条相关干预记录。超过时明确拒绝，不能截断后继续执行。
- 加签人须为同租户启用且具备实时审批 / 待读权限的用户；不能是申请人、当前处理人、冻结流程原有处理人或已经加入该流程的加签人。候选在数据库完成资格及排除过滤后真实分页。
- 加签子任务可以受控转交、抄送；转交不得把加签任务交回根处理人、其他加签参与者或冻结流程的其他处理人，防止通过转交绕过不同人员复核。只读抄送仍不授予审批权限。
- 任何加签拒绝都终止整个申请，取消其他待执行 / 等待任务并保留历史；撤回同样取消所有 PENDING 与 WAITING 任务。领域事务、人工接口、页面及受控工具已接线，完整回归通过前不视为交付。

## 当前证据

运行时模型先观察缺少实现的测试失败，再实现。首批 6 项通过；新增重复加签人 / 错误创建记录测试先失败，补严校验后 7 项全部通过。测试覆盖前加签恢复、后加签队列、并行 / 未来节点拒绝、子任务转交链及候选排除。

人工 HTTP 顺序链路先观察旧冻结节点唯一索引和等待子任务索引导致失败，随后以新迁移替换不适用于通用顺序队列的索引。原历史迁移未修改；加签仍保持单有效待办、根节点唯一及同根当前接收人唯一。

## 接口与受控工具

- `POST /api/generic-approval-tasks/{taskId}/add-sign`：`targetUserId`、`version`、`mode`（PRE / POST）、必填 `reason`。认证身份来自服务端；加签回执返回原任务、新任务、当前有效任务及版本，不声称审批完成。
- 候选接口 `purpose=ADD_SIGN`：服务端先校验原任务可加签，再按资格和已有复核人排除后分页。
- 任务详情增加 `canAddSign` 和有界 `addSignTasks`；任务行增加 `parentTaskId` 与 `addSignMode`。Agent 只投影有界字段及加签位置，不把完整流程历史或表单原文传给规划器。
- 新增代码白名单工具 `approval.genericTask.addSign`，L2 / SECONDARY / NEVER / SINGLE_WRITE，权限 `approval:act` + `todo:read`；AI Workspace 还需要真实待办页面权限。新增注册默认关闭，不改变租户写开关。
- `V202611111010` 只升级匹配已知旧哈希及安全属性的候选、详情读契约；不覆盖启用状态、自定义权限或未知契约。旧成功详情结果无需含新字段，仍可展示。

## 发布与回退边界

本批不发布线上、不主动启用工具。发布前仍需独立人工发布门。存在活动加签任务时禁止直接切回仅理解根任务的旧后端；应先关闭新加签入口，保留新运行时处理既有队列，待完成或人工撤回后再评估代码回退。不得删除历史动作或回退 Flyway 版本来隐藏队列。
