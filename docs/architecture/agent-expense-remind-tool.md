# 本人费用申请催办原子工具

## 能力与边界

`expense.remind` 向本人待审批费用申请的当前有效审批人发送一条站内通知。
只接受 `applicationId`（正整数）及 `version`（0–2147483646），不接受接收人、消息内容、
身份、租户、URL、表单或流程配置。通知内容由既有领域模板生成，不发送外部消息。

调用固定为 ToolGateway → 版本化写 Handler → `ExpenseToolPort` → 本地费用 Adapter →
`ExpenseApplicationService.remindAgentApplication` → `GenericApprovalService.remind`。
费用取消和催办共用按租户、申请人、固定费用表单与编号约束的 SQL 读取，不复制状态机。
成功回执包含申请编号、固定费用表单、PENDING 状态和新版本，通过共享导航定位本人费用详情。

## 安全契约

- 独立工具权限 `agent:tool:expense.remind`；费用领域再次检查实时 `route:approval-start`、`approval:remind`。
- L1、SELF、SINGLE_WRITE、EXPLICIT、NEVER、FULL_WRITE_AUDIT；最多一条、4096 字节、15 秒。
- Handler `1.0.0`，冻结 Schema Hash：
  `sha256:4a38437ed858eee879c9cadcf868a4f21e3ad0b70b17efa4dff6f1c73d5578d3`。
- 迁移 `V202610231200` 仅向已有 `approval:remind` 的角色添加工具权限种子；工具 `enabled=false`。
  全局与租户写开关不变，仍需独立人工发布门。

通用领域校验本人归属、PENDING 申请、运行流程、有效待办及乐观锁。
催办间隔复用已有服务端配置（当前默认 30 分钟，最少 1 分钟），使用待办条件更新防止并发重复。
同版本并发只能一次成功；结果不明时禁止自动重试，应先人工只读核验版本、通知和审计。

## 事务前置修复

真实 PostgreSQL 先复现了旧实现的缺陷：外层业务回滚后仍留下一条 REMIND 成功审计。
旧通知路径还会在提交前推入 Redis，无法随业务回滚。现仅对通用催办切换为：

1. 条件更新待办催办次数及时间、申请版本。
2. 记录审批动作流水。
3. `recordTransactional` 写入同事务业务审计。
4. `publishTransactional` 将站内通知直接写入同一数据库事务。

新通知方法要求 MANDATORY 事务，不入 Redis、不启动消费者、不外发消息；数据库异常向外传播。
普通通用催办与既有通用 Agent 催办同样受益。其他通知业务继续保留旧队列路径，
本节点不宣称全平台消息队列可靠性问题已解决，也不自动修改历史虚假审计或通知。

## 验证及回滚

定向门禁覆盖封闭参数、冻结 Hash、可信身份、费用归属、撤权、页面绑定、双语目录及真实回执定位。
真实 PostgreSQL 使用实际事务拦截器验证成功、限频、并发、通知失败、审计失败和外层回滚；
同时覆盖跨租户、跨用户、错误表单、非法状态和旧版本。测试仅在隔离 schema 写入业务夹具。

回滚先关闭工具、停止新增执行，再同步回退工具定义、Handler、端口、页面绑定和回执映射；
保留已执行 Flyway、业务状态、通知及审计。不要单独恢复独立成功审计或提交前队列通知，
否则会重新引入回滚后虚假成功；必要时应先停用催办写入口。
真实模型、Worker 与全页面浏览器端到端仍需验收，不能以代码工具数量代替全页面读写完成。
