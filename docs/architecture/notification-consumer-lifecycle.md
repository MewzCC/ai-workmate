# 通知消费者运行与关闭边界

## 问题与修复

本地后端在 Redis 未就绪时，每次消费失败都输出完整异常，原循环仅暂停 200 毫秒。
消费者没有绑定 Spring 销毁流程，关闭应用后可能继续访问已销毁的连接资源。

`NotificationServiceImpl` 保留通知发布和查询接口，把后台轮询交给包内的
`NotificationConsumerLoop`。连续运行失败采用 1、2、4、8、16、30 秒退避，之后保持
30 秒上限；正常空队列采用 200 毫秒暂停，成功取出后立即继续。正常轮询恢复后重置退避。

同一连续故障只记录一次异常类型摘要，不记录异常消息、堆栈或通知原文；恢复记录仅表示
一次轮询成功，不代表所有通知均已投递。手动 `consumeOne()` 保持失败返回 `false` 的兼容接口。

每个 Service 实例最多启动一个存活线程。Spring 销毁时先关闭运行标记，再中断并等待最多
5 秒；超时记录警告，不强行终止驱动。已关闭的实例不能重新启动。

## 安全与已知限制

没有新增工具、公共执行接口、依赖、迁移或配置开关；Agent 工具目录和 Gateway 校验不变。
消费者的重试只针对后续队列轮询，不重放业务写工具，不自动启用 Agent 写能力。

Redis List 的 BRPOP 与数据库落库之间原本就存在消息丢失窗口。本次只修复运行退避和
生命周期，不增加未经确认的自动重放，也不宣称可靠投递。后续需要独立的持久确认、幂等
和重放协议。生产端既有直接落库降级行为保持不变。

Redis 不可用仍是运行环境故障。健康接口成功、轮询退避正常，都不能替代真实模型、
Worker、浏览器及写能力人工发布验收。

## 验证方法

`NotificationServiceImplTest` 使用真实 Spring 容器验证销毁中断与重复启动保护；该场景
在修复前失败。`NotificationConsumerLoopTest` 通过注入等待函数验证真实循环调用、
退避上限、正常空轮询重置、连续消费、关闭期间异常和日志内容，不用实际长时间等待。

2026-10-24 定向 15 项通过；Java 17 `mvn clean test` 1439 项零失败、零错误，
10 项既有环境依赖测试跳过。本切片没有迁移，不把这些跳过项当作真实数据库或 Redis 验收。
OA 全量 54 个文件、415 项通过；lint 零错误（3 条既有警告），生产构建通过。

隔离开发实例在关闭 Agent 规划、执行、写入与清理开关，并禁用无关人事/附件 cron 后启动。
健康接口返回 200，Flyway validate 161 项且零待迁移。Redis 缺失的连续约 51 秒观察中，
消费者仅一条类型摘要，无恢复或投递成功的假日志；主动关闭时先记录消费者退出，再关闭数据库连接。
验证实例已停止，隔离端口无监听。没有通过这些结果宣称 Redis 或完整任务链就绪。

回滚时还原本切片文件即可，无数据库回滚步骤；旧实现会恢复高频日志及线程关闭缺陷。
